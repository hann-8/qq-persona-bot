## 3. 配置合同与迁移（LAP-09基础，LAP-10接参）

### 3.1 单一配置来源

本机`config/settings.local.yaml`仍是运行配置的唯一来源；示例留在`config/settings.example.yaml`，新增字段在实施时写入。不得复制账号或群号到可提交文档。以下是**目标字段**，不代表当前代码已识别：

```yaml
schema_version: 2
access:
  allowed_groups: ["REQUIRED_GROUP_ID"]
  blocked_users: []
  admin_users: ["REQUIRED_ADMIN_QQ"]
  private_enabled: false
llm:
  backend: codebuddy_cli
  model: deepseek-v4.1-flash
  reasoning_effort: auto
  context_window_tokens: null
  # 其余端口/队列/超时字段沿用已有值
chat:
  history_turns: 8
  context_input_limit_tokens: 16384
  context_overhead_reserve_tokens: 2048
  output_reserve_tokens: 2048
output:
  mode: plain_chat
  max_reply_chars: 1200
```

- `allowed_groups`：非空、去重后的群ID列表；空列表启动拒绝，绝不解释为所有群。管理员不豁免群白名单。
- `blocked_users`：全局发送者黑名单，默认空；管理员身份也不豁免。QQ号为规范数字字符串；拒绝bool、负数、空值、科学计数、混杂文字，整数输入可规范化为字符串。重复项显示已有，不重复保存。
- `llm.model`：当前站点实际模型ID，不是菜单展示名，不接受shell拼接。默认维持deepseek-v4.1-flash，只有操作者主动改配置才换。
- `reasoning_effort`：auto/minimal/low/medium/high/xhigh/max；auto按当前模型产品默认。显式值必须按模型能力验证，不能静默下调。CLI不支持或模型能力无法确认时按第5节处理。
- `context_window_tokens`：可选的CLI会话原生窗口档位，null表示不覆盖。只展示当前模型有证据支持的值；它与下面的输入预算不同，不允许伪造模型目录扩大容量。
- `context_input_limit_tokens`：主要供用户调整的模型输入预算，初始16384；范围1024—1048576的整数。已知模型容量/窗口更小时还须满足有效容量约束。小于固定system+本条输入所需预算时本条拒绝，不截断当前问题或system。未知模型真实容量不能据配置数字保证支持1M。
- 两个reserve初始各2048，允许0—65536；overhead计入输入预算，output用于预留回答/推理空间。它们是规划初值，不代表CLI隐藏prompt已精确测量，须在LAP-10验证并记录。不把max_reply_chars当输出token上限。
- `history_turns`：包含当前这轮的最大轮数，初始8、范围1—64；1表示本次不携带旧历史。历史仍按群+用户隔离，不增加群旁听或第二套记忆库。
- `output`：本轮仅plain_chat，保留1200字符上限（允许本机改为200—8000）；不增加Markdown切换、图片渲染或多消息模式。

### 3.2 读取、校验、写入与生效

1. config.py提取共享类型/加载/验证，gate、router、网关和配置工具读取同一规范，不在各处复制默认值。兼容UTF-8 BOM。
2. 旧配置缺schema_version按v1读：黑名单为空，模型沿用原值、强度auto、原生窗口null，chat/output补默认；正常启动只在内存补值，不悄悄重写用户文件。
3. 配置工具先完整读取并保留未修改/未知字段，再变更指定项、整份验证。用户未要求删除的本机参数不得丢失；不重新生成token。
4. 写前保存本机忽略路径`state/config-backups/`的带时间备份，临时文件与目标同目录，使用os.replace原子替换；失败不损坏旧配置。修改时对配置文件使用进程级独占锁，并比较读取时内容摘要，冲突即拒绝覆盖。
5. 第一版不做热重载。只读list/show可在运行中使用；配置工具写操作要求本项目已停止，避免gate/router/模型参数各用不同快照。手工编辑运行中的YAML仅下次启动生效，说明清楚。
6. 非法字段在启动任何项目子进程前拒绝。迁移/改模型不自动清空聊天库、不读取WorkBuddy认证文件或改用户全局设置。

新增`scripts/configure_bot.py`，提供控制台菜单和可脚本调用的子命令；根目录“配置机器人.cmd”直接调用项目Python，不依赖PowerShell执行策略或全局PATH。不要建立另一套WebUI或群内管理指令。

## 4. 授权群和黑名单（LAP-09）

- 不依赖QQ客户端拉黑：同群消息仍须由项目按sender user_id过滤。只能保证bot逻辑不处理，不能阻止QQ/NapCat接收平台网络事件。
- gate按“合法群事件、自身身份一致、非自身发送、授权群、发送者不在黑名单、当前真实At”判断，黑名单拒绝必须发生在forward、DedupStore.reserve及业务任务入库前；回复和模型调用都为0。
- router在建立trace、任务、会话、排队前做同样的黑名单防御。拒绝时静默，不发“你被拉黑”提示、不发冷却提醒。
- heartbeat/lifecycle/action echo不是用户消息，继续按现有传输规则处理，不能因新增过滤误丢。出站白名单不放宽；仅bot自己昵称的get_stranger_info例外保留。
- 黑名单针对原始发送者ID，不把文本中提及QQ号、转述或引用当作新发送者。继续不读取被引用消息正文、不展开转发、不处理其他群旁听。
- 拉黑不删除历史数据，也不承诺自动清除QQ/NapCat自身数据库；生效后的新消息不进入AstrBot/模型/新历史。恢复黑名单后原会话可按原规则继续，需清空时另走明确的会话重置。
- 不增加ban/kick等群管理能力，不自动加群；配置授权群不等于QQ账号已经在该群中，需文档说明由用户手工加入。

## 5. 模型、上下文、推理强度（LAP-10）

### 5.1 可用性依据与选定技术路线

2026-10-16只读核对官方独立CLI 2.168.0的`dist/codebuddy-headless.js`：存在`--effort <level>`、`--settings <file-or-json>`、`--input-format stream-json`；set_config handler允许contextWindow并可设置session override。未发现`--context-window`启动参数，不能凭名字编造一个。

官方[设置说明](https://www.codebuddy.cn/docs/cli/settings)描述reasoningEffort；[无头模式](https://www.codebuddy.cn/docs/cli/headless)描述JSONL输入和控制响应；[v2.158.0说明](https://www.codebuddy.cn/docs/cli/release-notes/v2.158.0)涉及set_config.contextWindow兼容调整。这些只支持能力候选，不等于本项目已经实测。`autoCompactWindow`只是压缩计算基准，**不能作为本轮上下文上限的替代**，也不能为了改上限启用额外模型压缩请求。

继续只用当前独立CLI，不为本轮切ACP/MCP、常驻代理或桌面UI自动化。优先用显式`--model`和`--effort`；原生窗口需要时使用**同一个请求子进程**的stream-json控制通道，AstrBot仍是唯一聊天历史维护者。

### 5.2 先做零推理控制验证，再接入业务

实施第一步单独验证控制协议，不先将新参数带入真实群服务：

1. 记录CLI版本/锁文件hash及相应handler位置；不得修改第三方bundle或为通过测试自动升级CLI。
2. 使用隔离请求目录与同样的无工具/无MCP/无自动记忆设置，验证`--settings`中的contextWindow是否在新会话被实际读取。它若只接受JSON但未进入session预算，判不通过，不能采用。优先选择经证明生效、无需常驻stdin控制的最小入口。
3. 若需stream-json，先以假进程测试状态机，再用实际CLI做**不发送user消息、不发起推理**的初始化/控制往返。每请求独立UUID；明确初始化/会话建立所需步骤，不用空白模型请求“创建会话”。
4. 控制请求候选形状如下；必须对照当前版本验证完整信封和会话建立时序，不能只因handler存在就直接上线：

```json
{"type":"control_request","request_id":"cfg-unique-id","request":{"subtype":"set_config","session_id":"per-request-session-id","config":{"contextWindow":200000}}}
```

5. 等待对应request_id的control_response，成功还须核对updated.contextWindow和errors；请求接受、响应回显不代表上游真实窗口已证实，进一步核对该会话effective budget。没有会话时的设置只能在确认CliSettingsProvider为进程内覆盖、不会写用户settings后使用。任何可能写全局配置的路径不用。
6. 不能在第一条模型请求开始后才改参数。需要发送业务user消息时只发1条，载荷仍是原system+历史JSON+当前问题，不能分别把每一条历史作为新的CLI回合重放。
7. 证明控制入口可用后再做有上限的实际provider验证。若无法在不追加模型轮次、不改全局设置的前提下设置原生档位，该项明确标“当前CLI未证实支持”；context_input_limit_tokens仍须实现，显式原生窗口设置应报清楚错误，不能静默忽略、退回其他后端或宣称三项全部完成。记录缺口供规划会话处理。

控制握手截止时间初始10秒，包含在同次请求总期限内，不额外延长90秒运行上限。超时/错误必须清理整个本次进程树且不发送user消息。stdin保持到必要控制/本次user消息被接收后再按已验证协议关闭，确保不因等待EOF挂起；收到最终result后及时退出/清理，不让长驻协议变成跨用户共享会话。

### 5.3 模型与强度的生效合同

- HTTP provider别名继续workbuddy-local；群友文本、HTTP客户端字段和人设不能改实际模型。所有实际参数来自本机验证后的配置快照。
- `--model`使用确切ID；ResultParser继续检查init的实际模型是否匹配，不因新模型而删除验证。若站点使用规范化ID，必须有显式映射证据，不直接取消比对。
- effort=auto不传强度覆盖；显式effort通过已验证的`--effort`或进程内settings传递。读取当前模型可用能力时只保留模型ID/原生窗口/支持强度等非敏感元数据，不读取/导出token。
- 模型支持强度列表已知时预先拒绝不支持项；未知时只允许auto，或先完成只读能力探测。CLI自身若会静默clamp，必须检测并显示requested/effective差异，不能把配置值当实际值。
- 账号可用模型由当前站点/套餐决定，不维护自动挑“免费模型”的策略；费用标记只能据用户当前界面或官方元数据记录时间，不保证长期免费。不可用时报模型/能力错误，不fallback收费API或其他模型。
- 不同步修改WorkBuddy/CodeBuddy用户全局settings；同账号不意味着桌面当前会话的模型、上下文、强度自动影响bot。

### 5.4 上下文预算算法

令B为context_input_limit_tokens，H为内部开销预留，O为输出/推理预留；W为有证据的有效原生窗口/最大输入约束。已知W时要求输入预算及O不超出模型对应容量；分别记录最大输入和总窗口，不能将两者混为一项。max_input_tokens约束应用于输入，W约束输入+O。

1. 合并固定边界system与人设，加入当前user问题，计算序列化后实际发送文本的预算；历史只取完整user/assistant对，排除DSML污染轮次。
2. 优先保留system和最新问题；历史从最旧的完整轮次逐对删除，直到“可见system+JSON对话+已知信封开销+H”不超过B，并满足history_turns。不能只统计聊天正文而漏JSON转义/角色标记。
3. 只有system+当前问题仍超限时，本条返回清楚的长度提示，CLI实际尝试为0；不得截断system、截半个问句或触发额外摘要模型请求。
4. 有经验证、与当前模型一致的本地tokenizer时精确计数。否则用明确标注的保守预算（初版按UTF-8字节数估算可见文本上界，并加H），不把字符数、字节数或未经验证的其他模型tokenizer称作真实token数。保留项目物理载荷/输出大小上限作为独立保护。
5. CLI内部附加prompt和服务端计费口径未完全可见，故估算不能承诺全请求/计费的严格token上界。状态显示“输入预算、计数方法、原生窗口已确认/未确认”；原生档位若成功设置可额外限制CLI会话预算，但不是“提高模型支持的最大窗口”。
6. 网关对最终规范请求再做同一预算校验；router负责裁剪历史，网关不自行生成第二份摘要或重排会话。contracts.py的24000字符/40消息限制、normalize_request调用点、router硬编码长度、AstrBot max_turns/trim_turns均须对齐新配置；合并system后的规范消息数最多2×history_turns（最大128）。HTTP载荷上限按min(8MiB, max(512KiB, 8×B字节))派生，保留8MiB绝对限制，超限明确拒绝；不能让较大预算仍被旧常量悄悄截住。
7. 旧聊天历史不做全库迁移。按当前配置取可用历史；模型更换默认继续已有纯文本历史，人设版本变化仍按既有行为创建新会话。不同模型的effort/window能力重新校验，不擅自沿用上一模型可用档位。

### 5.5 结果解析与隔离回归

ResultParser增加对应控制响应的分类/相关性检查，控制消息不当成模型result或群回复；重复/错request_id、errors、伪success、缺result、工具调用仍失败。保留init tools=[]/mcp_servers=[]、tool markup拒绝、子进程记忆禁用、无session持久化、每请求新上下文与单次CLI尝试。进程内显式关闭autoCompactEnabled并验证该开关的实际读取路径，防止较大上下文触发额外压缩推理；不能仅以--setting-sources none推断压缩已关闭。一个控制往返不是一次额外模型推理，统计应分别记控制配置和推理次数。

### 7.2 状态与未登录行为

| 模型 | not_probed / last_success / current_error | 本次未推理、最近成功时间、明确的模型错误类别 |
| 整体 | 结合进程+插件+QQ当前状态 | 只有通道已确认才能说“可接收群消息”；模型状态另列 |

实施要核对当前NapCat heartbeat的online字段；没有可靠字段时保留unknown，不能默认true。可使用现有允许的get_status/get_login_info作有界、带echo匹配的本机状态查询，但不扩大通用代理接口，不新增公开action入口。新状态查询与框架echo pending隔离，避免误吞框架回包。

health给last_error加发生时间/是否为历史记录，成功后当前状态与历史错误分开；不能因last_error非空把21:02旧失败一直显示成正在失败。QQ断开、模型认证失效、模型配额和发送ACK未知分开报告；不把所有情况归咎NapCat，也不擅自改写旧模型追踪的原因。

### 7.3 进程生命周期

1. 对整个start/stop操作使用同一OS级互斥锁，进程退出自动释放；锁文件存在不等于有人持锁。多个双击不得启动两套bot或交错改state。
2. 已完整启动再start：显示“已运行”及当前状态，成功返回，不重启/重配。部分组件存活则明确显示需要先关闭再启动，不顺手杀端口占用程序。
3. 未运行再stop：显示“已停止”，成功返回。状态文件陈旧时核对PID+创建时间，必要时校验受管路径，不碰PID已被其他程序复用的进程。
4. stop先暂停接收新任务，给予当前请求短暂有界退出期（初值5秒），随后取消/清理本项目子进程。可使用与本次实例ID/创建时间绑定的本机state停止标记，gate/router在准入前检查，保持已接任务出站通道；不得为此新开未认证的控制HTTP接口。启动清理已失效旧标记，不能用残留标记误停新实例。处理中任务按failed/unknown/send_unknown事实记录，重启不自动重放或重发。
5. 请求CLI可能在服务启动后生成，停止时还需跟踪受管服务进程的当前后代及创建身份；只终止项目所属树。停止状态原子保存，清理失败保留未退出进程身份，不能写空state冒充停止成功。
6. 启动失败只回收本次新建的受管进程，保留旧/外部进程。端口冲突报组件与端口，不抢占、不按进程名结束。NapCat独立目录、日常QQ路径和WorkBuddy原配置不修改。
