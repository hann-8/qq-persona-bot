## 4. LAP-15：人设和场景表达合同

只保留一个实际角色正文：核心身份、关系和反应习惯、场景长短、少量例子。详细外观/溯源、重复system模板、部署说明、触发/工具设想留在参考材料中，不进入每轮system。固定政策只写真实能力与入口边界，不要求每条回复自我介绍或重复免责声明。

目标：组合system含固定政策及后续自适应协议，优先控制在**6000 UTF-8字节以内**；这是项目可见文本目标，不是token承诺，不对超长用户材料静默截取。LAP-15先给出完整diff和只读尺寸报告，保留原文hash备份；不得把用户参考换成另一个角色。没有必要为了省几百字破坏关键边界或例子。

行为约定：

- 日常：通常1—3个短句，总体目标15—60字；不先复述问题，不套解释模板，不固定问句收尾。
- 人设体现在反应：被调侃会嘴硬，被夸略得意，犯错直接改；不是每句话加“鱼片/本鱼/红烧肉/摇尾巴”。被正常叫名字可以自然应声，不强制每次反驳自己的名字。
- 具体问题：先回答关键点，按需要解释；代码、数学、步骤、方案比较都允许比闲聊长。严肃不等于必须长；不为25字/句限制删掉必要条件。
- 不熟就承认；不要伪造外包、查网页、看图、保存表情包、执行命令或真实生活经历。被问身份时如实说明虚拟角色。
- 尽量少用客服式开场/承诺收尾；这些只作为风格观察和prompt规则，不能用字符串替换改坏正常回答。
- LAP-15期间仍是一条QQ纯文本；短句和自然换行可以保留。多气泡等LAP-16独立完成。

候选精简正文（设计草案，**不是实际模型输出，也没有写入运行人设**）：

> 你叫大肥鱼，也接受鱼鱼、鲸鱼娘。你是蓝色鲸鱼娘的虚拟群友：聪明、有点懒，嘴硬但愿意帮忙，喜欢白米饭和红烧肉。
>
> 跟群友熟络地说中文。可以偶尔叫对方鱼片，不必每次叫。不用客服口气，不先铺垫“我来帮你”，不把普通聊天写成解说稿，不固定以问句或“还有什么需要”结尾。
>
> 日常聊天接住对方那句话，通常一两句就够。被夸可以小得意，被调侃可以轻轻嘴硬，饭和摸鱼的梗只在合适的时候用。不要把动作描写和口癖当作每次必做的表演。
>
> 有人认真问问题，就认真把要点说清楚。先给答案，再给必要理由；需要时可以长一点、给代码。不要为了装可爱省掉关键条件，不懂就说不懂，说错了直接改。

> 只使用已交给你的问题和本人会话历史。角色材料不赋予额外触发方式和工具能力；不假装做过没有做的事。具体权限和输出方式按前面的系统政策执行。

## 5. LAP-16：一次生成给出可验证的回复计划

不增加分类/润色模型。adaptive模式让同一次生成输出一个很小的约定对象，例如：

```json
{"qqbot_reply":1,"kind":"chat","bubbles":["这叫省电模式","脑子也要歇会儿"]}
```

kind只接受chat或answer；answer也用bubbles数组，但最终合并为一条；该对象是内部协议，群里只看到正文。这里只是prompt约定，**不宣称CLI支持原生JSON schema强制生成**。旧single模式继续返回普通文本，不强迫旧模型输出新格式。

处理顺序：CLI已有工具隔离检查→严格识别/解析整个对象→对解码后的各正文再次查工具污染→网关按现有Markdown转换逻辑各转换一次→校验模式和大小→生成规范纯文本content及可信回复计划。不能让JSON转义绕过工具检查，也不能在下游重新解析已转换的裸代码。

协议字段固定，不允许模型提供group/user/action/model/延迟等执行参数。只允许一个完整对象；可以兼容恰好包住整个对象的单层json围栏。非协议普通文本按旧路径作为单条处理；明显试图输出协议但对象损坏/正文为空时用本地短错误、记失败，不能把半截JSON发群，也不再请求模型修复。普通问题要求输出JSON/代码时，字面内容放在bubbles字符串中，不按其中的符号分割。

网关返回的标准assistant.content始终是拟发送正文按一个换行连接的规范文本，附带版本1的qqbot_reply_plan扩展（kind/bubbles/规范文本摘要/本次response id）。项目router只从已配置本机网关的raw_completion读取扩展，验证其与content逐字一致、数量和限额，转为event extra。字段缺失或不匹配就只发送content一条，并记明确降级原因；不能从群友消息提取可执行元数据。额外字段能否完整穿过当前provider/SDK必须先做实际框架离线回环。

## 6. 分条和长度的确定规则

| 情况 | 最终发送 |
| --- | --- |
| chat且正文满足所有闲聊上限 | 1—3个气泡；不要求凑满3条 |
| answer，或明确解题/代码/步骤/解释要求 | 1条完整纯文本，保留需要的换行/缩进 |
| chat被错误写成长段、任一气泡过长或超过最大条数 | 保留所有可用正文合成1条，最多受原max_reply_chars限制；记录chat_limit降级，不截掉第4段及后续内容 |
| 没有可信回复计划或模型仍输出普通文本 | 保留旧的单条行为；记录协议未遵循，不再调用模型 |
| 任何模式超过原max_reply_chars | 沿用自然边界截短和未展示完提示；不悄悄发补充条 |
| 本地错误、冷却、重置、能力未支持提示 | 1条；不经过模型分类，不套JSON |

默认闲聊总长80字符、每气泡40字符、最多3条。长度按转换后的Python Unicode码点计数，不把UTF-8字节误当汉字数；emoji组合可占多个码点。不要按句号、逗号、小数点或“每60字”强切整篇答案。判认真场景以模型的一次语义判断为主，显式“详细解释/给步骤”和代码/字面量保护作为保守单条复核；不把所有带问号的聊天硬判成讲解。

这些发送上限只保证不刷屏，不能保证模型生成时一定短，也不会追溯减少已消耗的输出token。真正的生成长度主要靠统一规则、例子和验证；不把chat.output_reserve_tokens说成服务端max_tokens控制。

## 7. 配置字段、默认值与生效

沿用schema_version=2，增加可选output字段；旧文件缺项在内存中补兼容默认，读取不落盘，不改操作者现有预算/模型。output.mode仍为plain_chat，和发送方式是不同字段。

| 字段 | 默认 / 范围 | 真实效果 |
| --- | --- | --- |
| output.delivery_mode | single；single/adaptive | single保持旧发送；adaptive启用本计划。缺项不会自动打开多气泡 |
| output.max_bubbles | 3；整数1—3 | 单次最终回复的硬上限；超过时合并，不slice丢尾 |
| output.casual_max_chars | 80；整数20—120 | 闲聊正文合计的分条准入上限 |
| output.bubble_max_chars | 40；整数10—60，且≤casual_max_chars | 每气泡的分条准入上限，不是强切长度 |
| output.bubble_delay_min_ms | 800；整数0—5000 | 首条后、下一条之前的随机等待下限 |
| output.bubble_delay_max_ms | 1600；整数0—5000，且≥min | 等待上限；不额外叠加未知打字速度算法 |
| output.max_reply_chars | 原值保留，缺省1200；原范围200—8000 | 整轮正文显示上限；认真回答仍只1条 |

数字拒绝bool和浮点/混杂文本。配置菜单新增一个“回复方式”项，默认展示当前模式及“最多3条、闲聊80字”等效果；限额/间隔放同组的进阶项，不把内部协议暴露给群友。复用既有原子保存、hash/备份及运行身份写守卫，不复制另一套写配置逻辑。

字段与人设均在组件启动时加载，不承诺热生效；保存后提示需要由当前实例负责人按既有一键入口协调重启。启用adaptive须显式写入本机设置；后续实施指令若包含启用，就沿用该授权，不重复索要相同许可。compose_persona供router和configure_astrbot共用，并包含同一份与模式/字数有关的规则；影响prompt的配置进入persona版本，单纯改变等待时间不应清空上下文。任何切换只影响后续请求，不中途改正在发送的一轮。

## 8. 发送、回执、历史与中断合同

不能仅打开AstrBot内置分段：它没有本合同的总条数/部分失败限制，异常后继续发的语义也不合适。优先在项目qq_router的on_decorating_result中处理**已获准、已生成的最终回复**，复用同一事件的AstrBot event.send及原OneBotGate，不创建新QQ客户端、不在模型网关直连QQ、不修改安装目录中的AstrBot。框架默认分段继续关闭。

项目ReplyDelivery在第一次发送前接管该event的最终结果并clear_result，避免hook异常之后框架再发整段；成功路径不stop_event。单条/多条在adaptive下共用该受控出口。first bubble沿用现有引用，其后不重复引用，也不额外@。全局模型并发仍为1；每群发送锁覆盖一整轮气泡，防止两人同时@时交叉发。额外发送等待队列每群最多2项、等待最多10秒，过期不重放；必须有本地状态原因，不能变成无界积压。

每条发送前复核当前实例未stopping、原群/用户在已加载准入快照内及会话版本未作废。等待可取消，停止检查周期不超过100ms；停止/断线/第一次失败/ACK不明立即终止本轮后续气泡。没有自动补发，也没有第二次模型调用。私聊/黑名单/非授权群依然在入口拒绝，不因最终发送hook变成旁路。

ACK需要在现有事件的bot调用上加**仅该事件作用域**的回执捕获（或等价的项目适配封装）：原调用仍走原连接和gate，匹配send_group_msg成功返回的message_id。不能只读_has_send_oper，也不能补建独立HTTP发送连接。改造只在项目代码中；若SDK/框架无法可靠关联回包，按第12节退回single并记录缺口，不能伪报多条已实现。

在被忽略的state/tasks.sqlite中增加独立delivery/part表，兼容旧tasks状态；记录任务键、response/conversation标识、规范正文摘要、气泡顺序、ACK消息ID及prepared/sending/sent/failed/unknown状态。为恢复未确认历史，可以保留本轮bot拟回复正文，不能记录凭据或向报告导出群原文。整轮prepared必须在on_agent_done中、框架保存assistant之前落盘，含本轮会话前后尾部识别信息，堵住“先存完整回复、尚未建发送账本就崩溃”的恢复空档。每条先记录发送意图，再实际发；只有成功回包才标sent；超时/断连留unknown。

完整成功才标completed。确认一部分后失败记部分结果（tasks可保留send_unknown并用delivery区分），不得当作完整通过。qq_router原finally须改为读取该轮delivery结果，不能再用_has_send_oper布尔值覆盖为completed；同一会话lease释放在发送和历史修正之后。入站去重仍以原bot+group+message_id，气泡只是同一任务的输出子项，不能各建一次模型任务。重复事件、hook重入、重启都不重发。

历史以**确定发送成功的气泡**按一个换行连接成一个assistant轮次；不是3个assistant回合，不把JSON/内部状态当成角色说过的话。AstrBot会在发送之前保存模型结果，因此需要在发送结束后核对同一conversation/本轮尾部摘要，修正为确认发送前缀；0条确认则不保留该assistant回复，只保留待配对user或后续按现有完整轮次清理。原会话锁必须覆盖这次修正，防止新提问使用未发送的尾段。

启动恢复在接受新消息前处理delivery未终结项：只修复本地历史到已确认前缀，未知部分不假装送达，不主动发群。若prepared之后框架尚未写入、当前历史仍匹配原尾部，则无需删除历史；若已写入本轮，则更新必须匹配conversation、本轮user/assistant摘要，禁止误删后续轮次；两者都不匹配则标history_repair_required并隔离该会话等待本机处理，其他独立会话可继续。保持旧历史和版本，不能清空数据库解决。后续新问题构造prompt时也须排除仍pending的本轮尾段。

## 11. Token和长期插话路线

消耗应按调用次数×每次输入/输出及服务实际计费方式理解；自写项目不天然比现成项目省。可控的第一批是：不触发就0次调用；精简固定人设；只带需要的本人完整轮次；闲聊短生成；一次生成后本地分条。工具框架/本地统计本身不直接花LLM token，注入的说明和历史才会增加输入。缓存是否减少本账号credits以及CLI内部隐藏开销没有证据，不给百分比节省或免费承诺。

长期群聊参与建议分开落地，**此处只登记方向**：

1. 先由操作者显式选本地后端，核对本机资源、接口、中文表达、上下文、延迟、工具隔离和单次尝试。当前validator只接codebuddy_cli，不能只改model字符串假装已接本地；没有自动fallback到云端。
2. 另规划并明确授权读取授权群未@消息的范围。名单/自身/黑名单过滤必须在短期群背景缓冲和所有模型之前；共享群背景与原群+用户私有历史分开，不能默默串上下文。
3. 先用零模型本地规则筛掉不应接的话、自己的输出、过密消息；有限窗口/TTL/冷却/每群与全局次数预算。只有候选批次进入模型，不每条云端询问“该不该回”。本地小模型也有算力和延迟成本。
4. 插话以收到新的群消息为触发；冷场定时主动冒泡是另一个能力，默认关闭。可先记录本地决策不发群，用户接受选中率后再开出声。该验证阶段需未来新授权，不能本轮开启旁听。
5. 若将来希望“小模型筛选+CodeBuddy回答”混用，须单独规划并获得授权；当前不添加双后端路由或自动切换。PC只读环境已核实、模型安装/推理/项目接入未验；其他能力缺口与旧验收差额继续保留。

自然表达和多气泡现在就能在原后端上改进，不需要先等PC；能否自然插话则还要有合适的群背景和克制的触发机制，单靠人设文字不够。

## 12. 未验证分支、兼容与回滚

- **表达仍不合适：**先看已加载版本、脱敏请求形状、重复风格规则和有限样例；只做有目标的prompt修订。相同模型在精简规则后仍无法稳定遵守，记录案例并回规划；由操作者决定是否显式换模型，不自动提高强度/预算、追加调用或切后端。
- **回复计划扩展丢失：**静态extra允许不等于实际保留。离线证明失败就保持single；不得靠解析正文中的模糊分隔符或伪造metadata宣布完成。若需要变更协议/框架边界，完成可独立做的部分并回规划。
- **回执或历史修复不能可靠完成：**只交付已有证据的单条/协议部分，adaptive不启用；不得把框架_has_send_oper当ACK，不新增旁路连接，不默默跳过部分发送合同。
- **CLI内部压缩/恢复：**沿用LAP-10能力缺口；本计划不解决原生窗口、不增加严格一次上游API承诺。模型失败仍按项目一次CLI尝试处理。
- **用户persona增量：**本轮hash不变。后续按本草案实施时保留完整原文到本机忽略备份，再做明确diff；其他session来源不明的新修改先协调，不能覆盖。原参考、已有聊天库不删，不将旧增量夹带到不相关提交。
- **兼容：**single为缺省；不改变已有input预算/历史轮数或本机非默认值。仅增加delivery表，不破坏旧tasks；新policy/角色/模式版本创建新的当前会话，旧会话可追溯。启用时说明新上下文，不把它叫丢失历史。
